# 記事修正(edit-article)

leadus科目リポジトリのMarkdown記事1本について、指摘の妥当性を踏まえてその場で修正する。**編集を伴わない純粋なレビューのみの依頼は対象外**(その場合は[[review-article]]を使う)。

## ロール定義

このスキルはEditorロールをサブエージェント(Agent tool)として起動して構成する。オーケストレーター(このスキルを実行しているAgent自身)は、対象の特定・レビューの取得([[review-article]]の呼び出し)・Editorの起動・issue化の委譲・結果の提示のみを行い、**実行計画や編集そのものを自分自身で行わない**。

- **Editor**([references/editor.md](references/editor.md)): 採用済みの指摘をどう実行するか(即編集かissue化か)の計画権限と、対象ファイルを実際に修正する権限を持つ。**指摘が実際に対応する価値があるか(却下/採用)の判断は行わない**([[review-article]]側のTeacherが既に行っている)。

Student(初学者観点)・Professor(専門家観点)の読み取り専用レビュー、および指摘の却下/採用判断は、このスキル自身では実行しない。下記フローの「レビュー」「検証」の各ステップは、[[review-article]]スキルをSkill tool経由で呼び出す(両方+取捨選択モード)ことで取得する。review-articleはその内部でStudent・Professor・(却下/採用判断を行う)Teacherをそれぞれ独立したAgent toolのサブエージェントとして起動する。[[review-article]]の出力はデフォルトでは採用した指摘のみだが、このスキルは最終報告で却下理由も示す設計のため、**呼び出し時は必ず「却下した指摘も含めてほしい」と明示的に指定すること**。

Flow Aでは、初回レビュー(手順1)で起動されたStudent・ProfessorのAgentを、再チェック(手順4)で再利用する。これは無関係な新規指摘への発散を防ぐための意図的な設計であり、[[review-article]]の「Agentの再利用について」の仕組みに従う。Student/ProfessorへのSendMessageは必ず[[review-article]]経由で行い、このスキルが直接送ることはない。初回レビュー呼び出し時に返る(あるいはこの会話上で把握できる)Student・ProfessorのAgent識別子は、再チェック呼び出しまでオーケストレーターが保持しておくこと。

Editorを起動する際は、`subagent_type: general-purpose`、`model`は指定せず会話のデフォルトモデルを継承する。Agentはこの会話の履歴を一切持たないため、promptは自己完結させること(対象ファイルの絶対パス・対象リポジトリのルート・references/editor.mdの内容を全文そのまま・入力する指摘一覧(review-articleが採用したもの)または修正内容・呼び出し文脈(修正のみ/実行計画+修正のどちらか)を明記する)。

**スコープ逸脱への注意**: `general-purpose`は全ツールにアクセスできるため、指示していない範囲まで自発的に行う恐れがある。特に、自分自身が読み込んだファイル群からこのedit-articleスキル自身(SKILL.md等)を発見し、Skill/Agent toolで再帰的に呼び出してしまうケースに注意する。Editorのpromptの冒頭付近に必ず次のスコープ制約を含めること。

> 重要: あなたが実行するのはこのタスク単体です。他のAgentやサブタスクを起動しないでください(Agent toolを使わないでください)。スキル定義ファイル(SKILL.md等、edit-article関連のファイル)を探して読まないでください。このプロンプトに書かれている指示のみに従い、指定された出力フォーマットのみを返してください。

## 対象の特定

引数でファイルパスが与えられていなければユーザーに確認する。パスから対象リポジトリのルート(例: `/Users/toru/work/math`)を特定する。

## ユースケースと処理フロー

修正内容の指示がインプットとして得られたかどうかで、以下のフローを使い分ける。

### Flow A: 総合レビュー修正(デフォルト)

「この記事をレビューして直して」「批判して直して」のように、修正内容の指示(GitHub issueの内容やユーザーの明示的な指示)がインプットとして得られない依頼のデフォルト動作。この場合はRvから処理を開始する。

1. [[review-article]]スキル(両方+取捨選択モード、新規レビュー、却下した指摘も含める指定)を呼び出す(初回レビュー)。この時点でreview-article側のTeacherが却下/採用を判断済みである。このとき起動されたStudent・ProfessorのAgent識別子を、手順4で再利用するために保持しておく。
2. Editorを「実行計画+修正」文脈で起動する。手順1で採用された指摘一覧(却下されたものは含めない)をpromptに含め、二分類(即編集/issue化)と、即編集分の修正を行わせる。
3. issue化に分類された指摘があれば、[[create-issue]]スキルを呼び出して起票する(該当箇所・問題点・改善案をそのまま渡す)。起票前の確認はcreate-issueスキル自身の手順に従う。
4. 修正後の記事に対し、[[review-article]]スキル(両方+取捨選択モード、**再チェック**)を呼び出す(検証)。手順1で保持したStudent・ProfessorのAgent識別子を再利用する旨、手順1で採用された指摘一覧(即編集されたもの)、Editorが実際に行った変更内容(該当箇所の変更前後)を渡す。review-articleはこれを受けて新規スポーンせず、同一Agentへの絞り込んだ問い合わせ(解消したか・修正箇所の前後の文脈や全体整合性に新たな問題がないか)で検証する。
5. 検証結果を提示する。指摘が残っていても、ここで打ち切りユーザーに報告する(自動で修正ラウンドを繰り返さない)。

### Flow B: 検証付き修正

修正内容が既に具体化している場合に使う。例: GitHub issueの本文に基づく修正依頼、ユーザーが対象箇所・修正方向を明示した依頼。

1. Editorを「修正のみ」文脈で起動する。修正内容(issue本文またはユーザー指示)をpromptに含める。実行計画は行わせない。
2. 修正後の記事に対し、[[review-article]]スキル(両方+取捨選択モード、新規レビュー、却下した指摘も含める指定)を呼び出す(検証)。この記事に対する初回のRvなので再利用は行わない。「修正の意図」として、issueの「現状の問題点」「改善案」とEditorが実際に行った変更内容(手順1の出力)をあわせて渡す。これにより、Student・Professorのレビューを「この修正が課題を解決できているか」に焦点を絞らせ、無関係な新規指摘への発散を抑える。
3. 検証結果を提示する。指摘が残っていても、ここで打ち切りユーザーに報告する(自動で修正ラウンドを繰り返さない)。

## 出力する

会話内にMarkdownで直接提示する。ファイルへの保存は行わない。[[review-article]]・Editorの出力は要約・削減せず、そのまま転記する。review-articleが却下した指摘、issue化に留めた指摘、対応できなかった項目も省略せず含める(即編集された指摘だけを見せると、なぜ一部が反映されなかったか分からなくなるため)。

## スコープを超えないこと

- Git操作(ブランチ作成・コミット・push・PR作成)は行わない。作業ツリーのファイル編集のみ行う。コミット等が必要な場合はユーザーに委ねるか、[[fix-article]]の対象とする。
- 記事の大規模な構成変更(節の新設・並び替え・`requires`変更等)を直接実行しない。Editorの二分類基準(references/editor.md)に従い、該当する場合はissue化に留める。
- 現状は1記事ずつの呼び出しを前提とする。複数記事・ディレクトリ単位の一括処理への拡張は将来の課題とする。

## 注意

- **Editorの実行計画・編集は必ずAgent toolによるサブエージェントとして実行すること**。オーケストレーター自身が代行してはならない。
- 指摘の却下/採用判断は[[review-article]]側で完結している。このスキルのEditorが独自に却下判断を行うことはしない(実行段階で対応不能と判明した場合の「対応できなかった項目」への計上は除く)。
- Flow A・Bの検証で指摘が残った場合でも、修正・検証のラウンドを自動で繰り返さない(旧設計で「指摘がなくなるまで無限に繰り返す」ことによるトークン消費過多が問題になったため)。残った指摘はユーザーへの報告に含め、対応するかどうかの判断はユーザーに委ねる。
