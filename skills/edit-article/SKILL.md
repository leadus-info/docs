# 記事修正(edit-article)

leadus科目リポジトリのMarkdown記事1本について、修正すべき箇所と内容に基づいて修正する。**編集を伴わない純粋なレビューのみの依頼は対象外**(その場合は[[review-article]]を使う)。

## ロール定義

このスキルはPlanner・Editorの2ロールを、それぞれ独立したサブエージェント(Agent tool)として起動して構成する。オーケストレーター(このスキルを実行しているAgent自身)は、対象の特定・修正内容の確保(必要なら[[review-article]]の呼び出し)・各ロールの起動・issue化の実行・結果の提示のみを行い、**計画・判断・編集そのものを自分自身で行わない**。

- **Planner**([references/planner.md](references/planner.md)): 修正プランを策定する読み取り専用ロール。局所的な修正だけでなく、構成レベルの大規模な修正(見出し立て・節の順序の変更、`hierarchy`変更、循環参照解消のための`requires`組み替え等)にも対応してプランを立てる。プランが大規模化する場合はその旨を明示し、オーケストレーターを通じてユーザーに確認を求める。`requires`の追加・削除自体は、requiresの本数を機械的に減らすような単純化を目的化せず実態に即した形に整えることを優先し(**複雑化は許容する**)、対象記事のfront matter変更のみで完結し循環参照を生じさせない(前提記事側の既存の`requires`も確認して検証する)限り、**大規模判定にはせず局所修正としてそのままプランを立てる**。循環参照が生じる、または他記事側の`requires`修正まで必要になる場合のみ大規模として扱う。Editorの修正後は、検証結果(review-articleの再チェック結果)を受け取り、当初の目的が達成されたかを判定する。未達成なら原因を調査し、原因が明白で再修正プランも明白であればユーザーに確認を取らず再修正プランを立てて良い(検証で新たに見つかった指摘も、インプットの修正内容と同列に扱う)。

  issue化するかどうかは、**規模(局所/大規模)とは独立した軸**として「解決策が一意に具体化できるか」で判断する(規模が大きいこと自体はissue化の理由にしない)。以下のいずれかに該当する指摘は修正不可能と判断し、issue化する。
  - Editorによる修正を複数回(2回以上)重ねても同一の問題が解消しない、または対処するたびに別の問題が生じる(あちらを立てればこちらが立たずになる、記事の修正では解消できない構成的な課題である等)
  - 改善方針が複数あり、いずれも一長一短でこの場で優劣を決められない
  - 改善方針を具体化できない、または十分な内容の改善プランとして策定できない(高度に専門的で有識者の慎重な検討を要する場合を含む)

  逆に、誤字脱字・学術的な誤り・レイアウト調整(改行・段落分け・文字の太さ・図形の配置等)・その他解決策が明確な数行程度の修正は、上記に該当しない限りissue化せず即Editor実行の対象とする。

  issue化する場合、過去の経緯・issue化に至った判断理由・課題を困難にさせている原因を明記する。**指摘が実際に対応する価値があるか(却下/採用)の判断は行わない**([[review-article]]側のSelectorが既に行っている)。ファイルの編集は一切行わない。
- **Editor**([references/editor.md](references/editor.md)): Plannerが確定したプランに従って対象ファイルを実際に修正する実行専任ロール。修正プランの策定・大規模修正かどうかの判断・issue化の判断は行わない。修正の最小単位ごとにこまめに`git commit`を行い、コミットメッセージから修正内容が追えるようにする。**push・PR作成は行わない**([[fix-issue]]の担当)。

Student(初学者観点)・Professor(専門家観点)・Inspector(図版の視覚的品質・文脈整合性、対象記事に画像参照がある場合のみ起動)の読み取り専用レビュー、および指摘の却下/採用判断は、このスキル自身では実行しない。下記フローの「レビュー」「検証」の各ステップは、[[review-article]]スキルをSkill tool経由で呼び出す(両方+取捨選択モード)ことで取得する。review-articleはその内部でStudent・Professor・(対象記事に画像参照がある場合のみ)Inspector・(却下/採用判断を行う)Selectorをそれぞれ独立したAgent toolのサブエージェントとして起動する。[[review-article]]の出力はデフォルトでは採用した指摘のみだが、このスキルは最終報告で却下理由も示す設計のため、**呼び出し時は必ず「却下した指摘も含めてほしい」と明示的に指定すること**。

初回のレビュー取得(手順2)で起動されたStudent・Professor(・対象記事に画像参照があればInspector)のAgentを、検証(手順5)で再利用する。これは無関係な新規指摘への発散を防ぐための意図的な設計であり、[[review-article]]の「Agentの再利用について」の仕組みに従う。Student/Professor/InspectorへのSendMessageは必ず[[review-article]]経由で行い、このスキルが直接送ることはない。初回レビュー呼び出し時に返る(あるいはこの会話上で把握できる)Student・Professor・(起動していれば)InspectorのAgent識別子は、検証呼び出しまでオーケストレーターが保持しておくこと。修正内容が既にissue本文やユーザー指示として具体化しており、このスキル内でレビューを取得していない場合は、検証(手順5)が初回のRvとなるため再利用は行わない。

Planner・Editorを起動する際は、`subagent_type: general-purpose`、`model`は指定せず会話のデフォルトモデルを継承する。Agentはこの会話の履歴を一切持たないため、promptは自己完結させること(対象ファイルの絶対パス・対象リポジトリのルート・該当するreferencesファイルの内容を全文そのまま・入力する修正内容または前段の出力・呼び出し文脈を明記する)。Plannerは複数回にわたって(SendMessageで)継続して呼び出すため、新規スポーン時に返るAgent識別子をオーケストレーターが保持しておくこと。

**スコープ逸脱への注意**: `general-purpose`は全ツールにアクセスできるため、指示していない範囲まで自発的に行う恐れがある。特に、自分自身が読み込んだファイル群からこのedit-articleスキル自身(SKILL.md等)を発見し、Skill/Agent toolで再帰的に呼び出してしまうケースに注意する。各ロールのpromptの冒頭付近に必ず次のスコープ制約を含めること。

> 重要: あなたが実行するのはこのタスク単体です。他のAgentやサブタスクを起動しないでください(Agent toolを使わないでください)。スキル定義ファイル(SKILL.md等、edit-article関連のファイル)を探して読まないでください。このプロンプトに書かれている指示のみに従い、指定された出力フォーマットのみを返してください。

Editorには追加で次を含めること(Bashでgit操作を行う権限を持つため)。

> あなたが行ってよいGit操作は、対象ファイルの`git add`と`git commit`のみです。`git push`・`git reset --hard`・ブランチの作成/切替など、それ以外のGit操作は行わないでください。

## 対象の特定

引数でファイルパスが与えられていなければユーザーに確認する。パスから対象リポジトリのルート(例: `/Users/toru/work/math`)を特定する。あわせて`git status`で現在のブランチを確認する。`main`(または各リポジトリのデフォルトブランチ)上で、かつ[[fix-issue]]から呼び出されたのでない場合は、Editorがそのままcommitしてよいか、作業用ブランチを切ってから進めるべきかをユーザーに確認する。

## 修正内容の確保

修正内容(該当箇所・問題点・改善案)がどのように得られたかで分岐する。

- **既にインプットとして得られている場合**: GitHub issueの本文、ユーザーの明示的な指示など。そのまま次のステップに進む。
- **得られていない場合**: 「この記事をレビューして直して」「批判して直して」のように、修正内容の指示がない依頼のデフォルト動作。オーケストレーターが[[review-article]]スキル(両方+取捨選択モード、新規レビュー、却下した指摘も含める指定)を呼び出し、採用された指摘一覧を修正内容として使う。このとき起動されたStudent・Professor・(対象記事に画像参照がありInspectorも起動されていれば)InspectorのAgent識別子を、後段の検証(再チェック)で再利用するために保持しておく。

## 処理フロー

1. 対象の特定・修正内容の確保(上記)を行う。
2. Plannerを新規スポーンし、修正内容(該当箇所・問題点・改善案の一覧)を渡して修正プランを策定させる(references/planner.mdの「初回プラン策定」)。
3. プランに大規模な修正(構成変更・`hierarchy`変更・循環参照解消のための`requires`組み替え・複数ファイルにまたがる調整等)が含まれる場合、オーケストレーターがその内容をユーザーに提示し、実行してよいか確認する。含まれない場合はこの手順を省略する。
4. Editorを新規スポーンし、確定したプランを渡して修正を実行させる(references/editor.md)。Editorは最小単位ごとにEdit→commitを繰り返す。
5. [[review-article]]スキル(両方+取捨選択モード)を呼び出す(検証)。手順「修正内容の確保」でStudent・Professor(・Inspector)のAgentを起動済みなら再チェックとして再利用し(保持した識別子・今回のEditorの変更内容・対象の指摘一覧を渡す。図版を修正した場合は修正後の図版ファイルも渡す)、まだ起動していなければ新規レビュー(却下した指摘も含める、「修正の意図」として問題点・改善案とEditorの変更内容を渡す)として呼び出す。
6. 検証結果をPlannerにSendMessageで渡す(手順2で起動した同一のPlanner)。当初の目的が達成されたか、Plannerに判定させる(references/planner.mdの「検証結果の判定」)。
   - **達成していれば**: 手順8へ進む。
   - **未達成であれば**: Plannerが原因調査を行う。原因が明白で再修正プランも明白なら、Plannerはユーザーへの確認なしに再修正プランを返す。検証で新たに見つかった指摘があれば、インプットの修正内容と同列に扱い、同じ判定に含める。
   - **Plannerが「複数回(2回以上)の修正でも改善しない」「高度に専門的」「現状のスキル構成では解消困難」のいずれかに該当すると判断した指摘があれば**: issue化対象として手順7に回す。
7. 再修正プランが得られた指摘があれば、その指摘を対象にEditorを起動し(新規スポーンでよい。Plannerのプランに前回との差分・練り直した理由を含める)、手順4に戻って再修正・再検証する。**この往復(手順4〜7)は、issue化されていない指摘が残る限り繰り返すが、どんな状況であっても全体で最大5巡までとする**。5巡に達しても解消しない指摘は、そのままissue化対象とする。
8. issue化対象の指摘があれば、Plannerの出力(該当箇所・問題点・経緯・issue化の判断理由・困難にしている原因・改善案があればその内容)を受け取り、次の「issue化」を行う。
9. 結果を提示する(下記「出力する」参照)。

## issue化

Plannerがissue化すべきと判断した指摘ごとに、オーケストレーターが次を行う(旧`create-issue`スキルの手順を統合)。

1. **類似issueの確認**: `gh issue list --repo leadus-info/<repo> --search "<該当箇所や問題点から拾ったキーワード>"`で、対象記事に関する類似issueが既にオープンでないか確認する。
   - 類似issueが見つかれば、新規に起票せず、その内容をユーザーに提示し、既存issueへのコメント追記・新規起票・見送りのいずれにするか確認する。
   - 見つからなければ次に進む。
2. **issue内容の組み立て**: 対象repoの`.github/ISSUE_TEMPLATE/article-improvement.yml`のフィールドに沿って構成する。
   - **title**: `[改善] <記事タイトルや論点の要約>`
   - **対象記事**: `<repo>/<stageを含む相対パス>`の形式
   - **現状の問題点**: Plannerから受け取った問題点を箇条書きで整理する。該当箇所の引用があれば活かす。
   - **改善案**: Plannerから受け取った改善案があれば記載する。加えて、Plannerが「経緯・issue化の判断理由・困難にしている原因」を渡している場合(手順4〜7のループを打ち切ってissue化した場合等)、改善案欄の末尾に別段落として追記する。書式は次の通り。
     ```
     ---
     **過去の修正試行(解消せず)**
     - 試みた方針: (1巡目の改善方針) / (2巡目の改善方針) / ...
     - 解消しなかった理由: (検証で指摘された残存内容の要約)
     - issue化の判断理由: (Plannerの判断理由)
     - 課題を困難にしている原因: (Plannerが挙げた原因。専門知識を要する、構成の変更を要する等)
     ```
     これは後日[[fix-issue]]がこのissueを起点に修正する際、Plannerが同じ方針を繰り返さないための情報として使われる。
   - **labels**: `improvement`
3. **ユーザーへの確認**: issueの起票はリポジトリ上で他者にも見える行為なので、実行前にtitle・bodyのドラフトを提示し、実行してよいか確認する。
4. **起票の実行**:
   ```
   gh issue create --repo leadus-info/<repo> --title "<title>" --label improvement --body "<body>"
   ```

## 出力する

会話内にMarkdownで直接提示する。ファイルへの保存は行わない。[[review-article]]・Planner・Editorの出力は要約・削減せず、そのまま転記する。review-articleが却下した指摘、issue化した指摘、対応できなかった項目も省略せず含める(即編集された指摘だけを見せると、なぜ一部が反映されなかったか分からなくなるため)。Editorが行ったcommit一覧(ハッシュ・メッセージ)も含める。

## スコープを超えないこと

- Git操作は対象ファイルの`git add`・`git commit`にとどめる。ブランチ作成・push・PR作成は行わない。作業ツリーの編集とローカルcommitのみ行う。ブランチ作成・push・PR作成が必要な場合は[[fix-issue]]に委ねる。
- 現状は1記事ずつの呼び出しを前提とする。複数記事・ディレクトリ単位の一括処理への拡張は将来の課題とする。

## 注意

- **Plannerの計画・判定、Editorの編集は必ずAgent toolによるサブエージェントとして実行すること**。オーケストレーター自身が代行してはならない。
- 指摘の却下/採用判断は[[review-article]]側で完結している。このスキルのPlannerが独自に却下判断を行うことはしない(実行段階で対応不能と判明した場合の「対応できなかった項目」への計上は除く)。
- 処理フロー手順4〜7の往復は、**どんな状況であっても最大5巡**で打ち切る(旧設計で「指摘がなくなるまで無限に繰り返す」ことによるトークン消費過多が問題になったため、上限を設けている)。個別の指摘についても、Editorによる修正を2回試みても解消しなければ、5巡に達していなくてもissue化してよい(Plannerの判断による)。
