# issue起票(create-issue)

leadus科目リポジトリのMarkdown記事について、既に具体化している指摘内容(該当箇所・問題点・改善案)からGitHub issueを起票する。**指摘の収集(レビュー)や記事の修正は行わない**。指摘がまだ得られていない場合は[[review-article]]を、修正まで求められている場合は[[edit-article]]を使う。

## 入力

呼び出し元(オーケストレーターまたはユーザー)から次を受け取る。

- **対象repo**(例: `math`、`phys`)
- **対象記事の相対パス**(`<repo>/<stageを含む相対パス>`の形式、例: `math/advanced/analysis/derivatives.md`)
- **指摘一覧**: 指摘ごとに該当箇所・問題点・改善案(あれば)・重要度(impact: 1〜5、5が最も重大、あれば)。[[review-article]]のSelectorが採用した指摘では、改善案が**must**(修正後に満たされているべき条件)と**sample**(mustを満たす方法の一例)に書き分けられている。[[review-article]]のSelectorが採用した指摘には重要度が付与されている。ユーザーから直接依頼された場合など重要度が付与されていない指摘もある。
- **(任意)経緯情報**: [[edit-article]]のPlannerが検証ループを打ち切ってissue化した場合の「過去の修正試行(解消せず)」情報(試みた方針・解消しなかった理由・issue化の判断理由・困難にしている原因)。[[review-article]]から直接呼ばれた場合はこの情報はない。

指摘が複数件ある場合、原則として指摘(問題点)ごとに1issueとして個別に起票する。同一記事に対する指摘であっても、該当箇所や問題の性質が異なる別件であれば、まとめずそれぞれ起票する(1issue=1件の方が、後日[[fix-issue]]でのクローズ判定・優先度付け・PRとの対応が明確になるため)。次のいずれかに該当し、実質的に同一の指摘とみなせる場合に限り、1issueにまとめてよい(問題点欄で箇条書きにする)。

- 同じ問題点(同一の原因・同一の改善方針)が記事内の複数箇所に繰り返し現れている場合
- 複数の指摘が互いに強く関連し、一方を直さなければ他方も直せない(または直しても意味がない)など、実質的に不可分な場合

上記に該当しないのにまとめて起票したい事情がある場合は、ユーザーに確認した上でまとめてもよい。

## 手順

指摘(または1記事分にまとめた指摘グループ)ごとに次を行う。

1. **類似issueの確認**: `gh issue list --repo leadus-info/<repo> --search "<該当箇所や問題点から拾ったキーワード>"`で、対象記事に関する類似issueが既にオープンでないか確認する。
   - 類似issueが見つかれば、新規に起票せず、その内容をユーザーに提示し、既存issueへのコメント追記・新規起票・見送りのいずれにするか確認する。
   - 見つからなければ次に進む。
2. **issue内容の組み立て**: 対象repoの`.github/ISSUE_TEMPLATE/article-improvement.yml`のフィールドに沿って構成する。
   - **title**: `[改善] <記事タイトルや論点の要約>`
   - **対象記事**: `<repo>/<stageを含む相対パス>`の形式
   - **現状の問題点**: 受け取った問題点を箇条書きで整理する。該当箇所の引用があれば活かす。
   - **改善案**: 受け取った指摘にmust・sampleがあれば、次の見出しで書き分けて記載する。mustとsampleの区別は崩さない(sampleをmustとして書かない)。
     ```
     **満たすべき条件(must)**
     - (must)

     **改善案の一例(sample。この通りに直す必要はなく、mustを満たす別の方法でもよい)**
     - (sample。「なし」なら「なし」と書く)
     ```
     must・sampleに書き分けられていない改善案(ユーザーから直接依頼された場合等)は、受け取った改善案をそのまま記載する。加えて、呼び出し元から経緯情報(過去の修正試行)を渡されている場合、改善案欄の末尾に別段落として追記する。書式は次の通り。
     ```
     ---
     **過去の修正試行(解消せず)**
     - 試みた方針: (1巡目の改善方針) / (2巡目の改善方針) / ...
     - 解消しなかった理由: (検証で指摘された残存内容の要約)
     - issue化の判断理由: (呼び出し元から受け取った判断理由)
     - 課題を困難にしている原因: (呼び出し元から受け取った原因。専門知識を要する、構成の変更を要する等)
     ```
     これは後日[[fix-issue]]がこのissueを起点に修正する際、[[edit-article]]のPlannerが同じ方針を繰り返さないための情報として使われる。
   - **labels**: 指摘一覧に重要度(impact)が付与されていれば、それをそのまま使う(複数指摘をまとめた場合は最も深刻な指摘に合わせる)。付与されていない場合(ユーザーから直接依頼された場合等)は、次の5段階から自身で1つ選ぶ(数値が大きいほど重大)。
     - `impact: 5` — 論理が破綻していて読者がgoalに到達できない、誤った理解に導かれる(論理的飛躍で結論が導出不能、記号矛盾で計算が破綻、図と本文の矛盾、複数記事間での定義の矛盾、内容を誤らせる誤字など)
     - `impact: 4` — 誤解を招く記載(計算ミス、用語の誤用、内容に影響する誤字等)。正確性を損なうが記事全体の結論や論理構造までは破綻しない
     - `impact: 3` — goal到達に必要な情報そのものが本文に欠落している(論理の飛躍・説明不足が深刻で、読者が自力で補うことができない)
     - `impact: 2` — 必要な情報自体は本文にあるが、行間・接続を読者が自力で埋める負荷が高い(Rv指摘のうち量的なボリュームゾーンはここに該当しやすい)
     - `impact: 1` — 読了に支障はないが改善余地がある些末な点(用語の初出が括弧書き、軽微な表記のばらつきなど)
3. **ユーザーへの確認**: issueの起票はリポジトリ上で他者にも見える行為なので、実行前にtitle・bodyのドラフトを提示し、選んだimpactラベルとともに実行してよいか確認する。
4. **起票の実行**:
   ```
   gh issue create --repo leadus-info/<repo> --title "<title>" --label "impact: <1-5>" --body "<body>"
   ```
   対象repoに`impact: <1-5>`のラベルが存在しない場合は、`gh label create`で次の色で先に作成する(既存の`impact: high/medium/low`ラベルからの移行時など)。最重大の5のみ黒とし、4〜1は暖色(重大)から寒色(軽微)へのグラデーション(赤→オレンジ→緑→青)で統一している(GitHub上でのラベル文字は白抜き表示)。

   | label | color |
   | --- | --- |
   | `impact: 5` | `#000000` |
   | `impact: 4` | `#B60205` |
   | `impact: 3` | `#ec5600` |
   | `impact: 2` | `#0E8A16` |
   | `impact: 1` | `#147ad9` |

   ```
   gh label create "impact: 5" --repo leadus-info/<repo> --color 000000 --force
   gh label create "impact: 4" --repo leadus-info/<repo> --color B60205 --force
   gh label create "impact: 3" --repo leadus-info/<repo> --color ec5600 --force
   gh label create "impact: 2" --repo leadus-info/<repo> --color 0E8A16 --force
   gh label create "impact: 1" --repo leadus-info/<repo> --color 147ad9 --force
   ```

## 出力する

会話内にMarkdownで直接提示する。起票したissue(または見送った・既存issueに追記した)の一覧を、URLとともに示す。

```markdown
## 起票したissue

- <title> (impact: <1-5>) — <issue URL>
- ...
(なければ「なし」)

## 見送った・既存issueに追記した項目

- (該当箇所・問題点の要約): 見送り / 既存issue追記(<issue URL>)、理由
- ...
(なければ「なし」)
```

## スコープを超えないこと

- 記事の修正・レビュー・指摘の収集は行わない。指摘が得られていない場合は呼び出し元に[[review-article]]の実行を促す。
- issueの起票はユーザー確認を経てから実行する。無断で`gh issue create`を実行しない。

## 参考

2026-08-29、Rv指摘の運用方針が「軽微なものは即座にその場で修正する」から「[[review-article]]のSelectorが採用した指摘は原則すべてissue化する」へ転換されたことに伴い、[[review-article]]の出力を直接issue化する導線が必要になり、新設した。

旧`create-issue`は2026-08-23に[[edit-article]]へ統合されていた(詳細は[[edit-article]]の参考参照)。統合の理由は当時`edit-article`からしか呼ばれておらず独立スキルとして持つ意義が薄かったためだったが、今回[[review-article]]からも直接呼ばれる用途が生まれたことでこの前提が変わったため、`edit-article`内の「issue化」セクション(類似issue確認・テンプレート組み立て・ユーザー確認・起票)をほぼそのまま移植する形で独立スキルとして再分離した。

これに伴い、`edit-article`側は「修正内容が得られていない場合に[[review-article]]を呼んで採用指摘を修正内容として使う」経路(旧Flow A相当)を廃止し、修正内容(issueの本文やユーザーの明示的な指示)が既に具体化していることを前提とするスキルに純化された。Rv由来の指摘は、オーケストレーターが[[review-article]]→本スキルの順に直接連携させる運用になった(詳細は[[edit-article]]の参考参照)。

2026-08-30、issue化して初めて重要度(impact)がわかるのでは、Rv結果を見た時点で重要度が伝わらないという指摘を受け、重要度判定のタイミングを[[review-article]]のSelectorに前倒しした(詳細は[[review-article]]の参考参照)。これに伴い、本スキルのlabels判定は「指摘一覧に重要度が付与されていればそれをそのまま使う」を優先経路とし、従来の3段階基準による自身での判定は、重要度が付与されていない場合(ユーザーから直接依頼された場合等)のfallbackとして残した。

2026-08-30、同一記事への複数指摘の起票粒度を「原則1記事1issue、別々に追跡したい場合のみユーザー確認の上で分割」から「原則指摘ごとに1issue、実質的に同一の指摘とみなせる場合のみまとめる」へ転換した。1issueに無関係な複数件をまとめると、後日[[fix-issue]]で一部の指摘だけ対応できてもissueをクローズしづらく、PRにも無関係な修正が混ざりやすいという運用上の問題があったため。

2026-09-01、[[review-article]]側でimpactが3段階(high/medium/low)から5段階(数値1〜5、5が最も重大)に再設計されたことに伴い、本スキルのfallback判定基準・labels形式を同期した(詳細は[[review-article]]の参考参照)。ラベル表記は`impact: high`のような名前付きではなく`impact: 1`〜`impact: 5`の数値のみとし、GitHub上でのソートしやすさを優先した。既存リポジトリに旧`impact: high/medium/low`ラベルが残っている場合は、起票時に新ラベルが存在しなければ`gh label create`で作成する運用とした。あわせて、数値が大きいほど暖色(赤→オレンジ→黄→緑→青)になるグラデーションでラベル色を定めた(`impact: 5`=`#B60205`、`impact: 4`=`#e8683d`、`impact: 3`=`#dfb300`、`impact: 2`=`#0E8A16`、`impact: 1`=`#78aee0`)。ラベル文字を白にしたいという要望を受け、輝度計算(YIQ・WCAG相対輝度)上は`impact: 4`・`impact: 3`・`impact: 1`が黒文字表示になる可能性がある色に見えたため一時的に明度を落とした色に変更したが、実際のGitHub上の表示を確認した結果、この色のままで文字は白抜き表示になることが確認されたため、いったん上記の色に確定した。

2026-09-02、視認性の懸念があった黄色(`impact: 3`)をやめ、最重大の5だけ黒にして「別格の重大さ」を強調する配色に変更した(`impact: 5`=`#000000`、`impact: 4`=`#B60205`、`impact: 3`=`#ec5600`、`impact: 2`=`#0E8A16`、`impact: 1`=`#147ad9`)。4以下は赤→オレンジ→緑→青の暖色→寒色グラデーションを維持している。

2026-10-26、[[review-article]]のSelectorが採用した指摘を**must**(修正後に満たされているべき条件)と**sample**(mustを満たす方法の一例)に書き分けるようになったのに伴い、issue本文の「改善案」欄でもこの2つを見出しで書き分けるようにした(詳細は[[review-article]]の参考参照)。issueの改善案が修正の仕様としてそのまま扱われ、改善案の方法に引きずられた修正が行われる問題を防ぐため。issueテンプレート(`article-improvement.yml`)のフィールド構成は変えず、「改善案」欄の中で書き分ける。
