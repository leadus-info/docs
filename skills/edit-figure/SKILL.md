# SVG図版の作成・修正(edit-figure)

leadus科目リポジトリのMarkdown記事1本に対し、教科書的な線画スタイルのSVG図版を新規に作成して本文中に挿入する、または既存のSVG図版を修正する。対象は幾何図形・関数グラフ・座標系・物理の図示(自由体図、v-tグラフ、光線図、回路図など)。新規作成・既存修正のどちらのユースケースでも、規約読み込み・SVG設計・レンダリング確認の手順は共通のため1スキルで扱う。

## モードの特定

引数・ユーザーの発言から、次のいずれかを判定する。

- **新規作成**: まだ存在しない図をこれから作る(「この記事に図を入れて」等)。
- **既存修正**: 既にあるSVGファイルを直す(「〇〇.svgを直して」、[[review-article]]のInspector指摘を受けての修正等)。**指摘の妥当性判断(直すべきかどうか)は行わない**。[[review-article]]のSelector・[[edit-article]]のPlannerが既に採用済みと判断した指摘、またはユーザーの明示的な指示を、そのまま実行対象として受け取る。

どちらか判別しづらい場合はユーザーに確認する。

## 手順

### 0. 対象を特定する

- 引数でファイルパスが与えられていなければユーザーに確認する。パスから対象リポジトリのルート(例: `/Users/toru/work/math`, `/Users/toru/work/phys`)を特定する。
- **新規作成の場合**: 対象記事のパスを特定する。「何を描くか」が引数やユーザーの発言で指定されていればそれに従う。指定がなければ記事本文を読み、図があると理解の助けになる箇所(視覚化すると早く飲み込める定義・図形、数式のグラフ、向きや大きさが本質的な量、位置関係の説明など)を洗い出し、2〜4件程度をAskUserQuestionで提示してユーザーに選んでもらう。記事全体を図で埋め尽くす必要はない。本当に理解の助けになる箇所だけに絞る。
- **既存修正の場合**: 対象SVGファイルのパスと、修正内容(該当観点・問題点・改善の方向性。[[edit-article]]からは修正後に満たすべき条件(must)と改善方針の形で渡される)を特定する。呼び出し元(ユーザーまたは[[edit-article]])からこれらが得られていない場合はユーザーに確認する。修正対象の図が挿入されている記事のパスもあわせて特定する(規約確認・文脈整合性の判断に使う)。

### 1. 対象リポジトリの規約を読み込む

- 同リポジトリの`CONTRIBUTING.md`(記載ルール共通)と`GUID.md`(科目固有の記法・図の規約)を読む。
- `GUID.md`の「図・グラフについて」節を確認し、保存先ディレクトリ構成(`<topic>/images/`)、形式(SVGまたはPNG)、alt text必須、科目固有の追加要件(例: 物理では軸に物理量と単位を明記しベクトルは矢印で示す)を把握する。
- `GUID.md`の「記号・表記の統一」節を確認し、図中のラベルに使う記号・書式(例: 物理でのベクトルの太字表記$\boldsymbol{F}$、単位表記のルール)を本文の記法と整合させる。
- 科目固有のルールをこのスキルにハードコードしない。必ずその場で読み直す。将来他科目リポジトリが増えても同じ手順で対応するため。

### 2. SVGを設計する(新規作成)/ 修正方針を立てる(既存修正)

本サイトは教科書であることを踏まえ、装飾を排した簡潔なスタイルにする。具体的な数値基準・サンプルは[references/svg-style.md](references/svg-style.md)を参照。要点:

- 線画中心。塗り・グラデーション・影・過剰な色数を避ける。
- 線・文字の色は`currentColor`を基本とし、ページ側のテーマ(ライト/ダーク)に自動追従させる。複数の量を区別する必要がある場合も色相を増やさず、線種(実線/破線)やラベルで区別する。
- `viewBox`で座標系を定義し、固定`width`/`height`属性は付けない(表示先の幅に応じて拡大縮小させるため)。
- 線の太さ・フォントサイズ・矢印(マーカー)の様式は記事間で揺れないよう、references記載の基準値に揃える。
- ラベル・数値・記号は手順1で確認した科目のGUID.md記法に合わせる。
- 説明に必要な要素だけを描く。無関係な装飾・背景・不要な補助線を入れない。
- **立体(立方体・直方体・角柱など)を斜投影(オブリーク投影)で描く場合は、平面図形・グラフとは別の投影法上の注意点があるため[references/solid-figures.md](references/solid-figures.md)を参照する。座標計算だけでは正しい比率かどうか判断できない(奥行き線を正面の辺と同じ長さにすると、直感に反して間延びして見える)ため、必ず次のレンダリング確認を行う。**

**既存修正の場合**は、まず対象SVGファイルを読み、[[review-article]]のInspector等から渡された修正内容(該当観点・問題点)を踏まえて、上記の基準に照らしどこをどう変えるかを検討する。指摘されていない箇所を無関係に書き直さない(最小限の差分にとどめる)。

### 2.5. レンダリングして目視確認する(新規作成・既存修正いずれも必須)

座標を計算・変更しただけでは、実際の見た目(比率・立体感・重なり)を正しく予測できないことが多い。**既存修正の場合も、修正前の状態と見比べて実際に問題が解消したかを必ず確認する**(座標上は直したはずでも、視覚的に解消していないことがある)。

- `python3 -m pip install cairosvg`(未導入なら)。
- 以下でSVGをPNGに変換し、Readツールで画像として確認する。

  ```python
  import cairosvg
  with open("path/to/figure.svg") as f:
      svg = f.read()
  cairosvg.svg2png(bytestring=svg.replace("currentColor", "black").encode(),
                    write_to="/tmp/preview.png", scale=3, background_color="white")
  ```

- 見て違和感があれば(潰れて見える、間延びして見える、意図した形に見えない、文字が重なっている等)、座標を調整して再レンダリングする。「座標上は正しいはず」で押し切らず、実際に見えた形を判断基準にする。
- 複数の候補パラメータで迷う場合は、比較用に単純化した図(対象の要素1つだけ)を複数パターン並べてレンダリングし、見比べてから本番の図に反映すると手戻りが少ない。

### 3. ファイルを保存する

- **新規作成**: 保存先は対象記事と同じディレクトリの`<topic名>/images/<figure-name>.svg`(`GUID.md`の規約通り)。ディレクトリが存在しなければ作成する。ファイル名はkebab-caseで内容が分かる名前にする(例: `interior-angle-sum.svg`)。
- **既存修正**: 既存ファイルを直接書き換える(ファイル名・保存先は変更しない)。

### 4. Markdownに挿入する(新規作成のみ)

- 該当する説明の直後など、文脈上自然な位置に`![altテキスト](<topic名>/images/<figure-name>.svg)`を挿入する(記事本文と画像ファイルの相対パス関係に注意)。
- alt textは図の内容を過不足なく説明する日本語にする。装飾目的ではなく内容理解に必須の図なので省略しない。
- 見出し直後や`---`区切りをまたいで文脈と無関係な位置に置かない。
- **既存修正でalt textの内容も変える必要がある場合**は、この手順に準じて該当箇所を書き換える。

### 5. commitする

呼び出し元からcommitしないよう指定された場合([[edit-article]]からの呼び出し)は、この手順を行わず、変更を未commitのまま残す。commitは呼び出し元が行う。

- `git add <対象ファイル>` → `git commit`を行う。新規作成でMarkdown本文も変更した場合は、SVGファイルとMarkdownファイルをまとめて1つのcommitにしてよい。
- コミットメッセージは、対象リポジトリに既存のコミット規約があればそれに従う。なければ、変更内容が分かる簡潔な日本語1行(例: 新規作成は`derivatives.md: 接線の図を追加`、既存修正は`interior-angle-sum.svg: ラベルの重なりを解消`)とする。
- **あなたが行ってよいGit操作は`git add`と`git commit`のみ**。`git push`・`git reset --hard`・ブランチの作成/切替など、それ以外のGit操作は行わない。
- コミット対象は、今回の作業で実際に変更・作成したファイルのみに限定する(`git add -A`等で無関係な変更を巻き込まない)。

### 6. 報告する

- **新規作成**: 作成したSVGファイルのパスと、挿入したMarkdown上の位置(該当見出し名など)、commitハッシュを簡潔に報告する。
- **既存修正**: 修正したSVGファイルのパス、対応した指摘の要約、実際に行った変更内容、commitハッシュ(commitした場合)を簡潔に報告する。呼び出し元が[[edit-article]]の場合は、Editorの出力フォーマット(`## 実施した修正`)に準じた形で返してよい。

## 注意

- 1回の呼び出しで対象とするのは記事1本・図版1点。複数記事・ディレクトリ単位への一括生成・一括修正は将来の拡張とする。
- このスキルは図の作成・修正・挿入のみを担当する。記事本文の内容批判・網羅性チェックはreview-article・edit-article/compare-curriculumに委ねる。図の視覚的な問題点の指摘・修正要否の判断は[[review-article]]のInspectorが行う(このスキルは指摘を受けて実行するだけで、指摘の妥当性を判断し直さない)。
- 新規作成の場合、図が本当に必要か迷ったら無理に作らず「この記事には図が不要」と判断してよい。図を作ること自体が目的化しないようにする。
- 既存修正の場合、渡された指摘の範囲を超えて図全体を作り直さない(最小限の差分にとどめる)。
