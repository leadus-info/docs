# 記事批判レビュー(review-article)

leadus科目リポジトリのMarkdown記事1本について、「概要レベルで終わっていないか」「論理が飛んでいないか」「読者に不親切な箇所がないか」を批判的に検証する。対象は内容の深さ・厳密さ・明瞭さであり、フォーマットや表記ルールの遵守チェックではない。

検証は性質の異なる2種類のサブエージェントに必ず委譲する。オーケストレーター(このスキルを実行しているAgent自身)は、対象の特定とサブエージェントの起動・結果の提示のみを行い、**10観点分析やロールプレイ読解を自分自身で行わない**。

- **Agent A(学術的正確性Rv)**: 対象分野の専門家として、10観点で学術的な正確さ・厳密さを評価する。
- **Agent B(読者追走テストRv)**: stage相当の、認知能力を抑えた読者として記事を実際に先頭から読み進め、つまずいた箇所を記録する。低い認知能力を再現するため、Agent tool起動時に`model`パラメータへ`haiku`を指定する(プロンプトによるペルソナ演技だけに頼らない)。

## 手順

### 0. 対象記事を特定する

引数でファイルパスが与えられていなければユーザーに確認する。パスから対象リポジトリのルート(例: `/Users/toru/work/math`)を特定する。

### 1. Agent A・Agent Bを並行して起動する

同一メッセージ内でAgent toolを2回呼び出し(`run_in_background: false`で両方の完了を待つ)。各Agentはこの会話の履歴を一切持たないため、promptは自己完結させること(対象ファイルの絶対パス・リポジトリルート・読むべきファイル・分析観点・出力フォーマットをすべて明記する)。オーケストレーター自身は記事本文やCONTRIBUTING.md等を先回りして読み込まない(各Agentが自分で読む)。

#### Agent A: 学術的正確性Rv

- `subagent_type`: `general-purpose`
- `model`: 指定しない(会話のデフォルトモデルを継承する)
- promptに含めるもの:
  - 役割設定: 「あなたは対象科目分野の専門家です。学術的な正確さ・論理的厳密さを最優先して評価してください。」
  - 対象記事の絶対パス、対象リポジトリのルート
  - 読むべきファイル: 対象記事本体(front matter含む: `title`/`goal`/`stage`/`subject`/`hierarchy`/`requires`)、同リポジトリの`CONTRIBUTING.md`(stage別チェックリスト)・`GUID.md`(科目固有の記法・出典ルール)、front matterの`requires`に列挙された前提記事(相対パスから実ファイルを解決して読む)、本文中でリンクされている関連記事(「関連ページ」節など。リンク先が実在するかも確認する)、判断に迷う場合は`MANIFEST.md`(中立性の原則)
  - 下記「## Agent A: 10の観点」の全文(要約せずそのまま渡す)
  - 下記「Agent Aの出力フォーマット」
  - 下記「## 注意」のうちAgent Aに関わる内容

#### Agent B: 読者追走テストRv

- `subagent_type`: `general-purpose`
- `model`: `haiku`(認知能力を抑えた読者を演じさせるため、意図的に非力なモデルを使う)
- promptに含めるもの:
  - 対象記事の絶対パス、front matterの`stage`の値
  - 下記「## Agent B: 読者ペルソナ」の全文
  - 下記「## Agent B: 読み進め方」の全文
  - 下記「Agent Bの出力フォーマット」

### 2. 出力する

会話内にMarkdownで直接提示する。ファイルへの保存は行わない。Agent A・Agent Bの結果を要約・削減せず、そのまま2部構成で転記する。

```markdown
## 1. 学術的正確性レビュー(専門家Agent)

(Agent Aの出力をそのまま)

## 2. 読者追走テスト(ロールプレイAgent)

(Agent Bの出力をそのまま)
```

### 3. スコープを超えないこと

このスキルは指摘のみを行い、記事の書き直し・加筆は行わない。改稿が必要な場合はその旨をユーザーに伝え、対応は別途の依頼に委ねる。

## Agent A: 10の観点

数値目標(行数・スコア・パーセンテージ)は一切使わず、すべて定性的に判断する。**問題が実際にあると判断した場合にのみ指摘する。指摘のための指摘をしない**(下記「注意」も参照)。各観点の箇条書きは判定の着眼点であり、チェックリストの機械的消化ではなく判断材料として使う。

1. **goalの充足**: front matterの`goal`達成に読者が身につけるべき知識・スキルを洗い出し、本文が過不足なくカバーしているか確認する。
   - 用語の定義や概要紹介だけで終わり、使い方・具体例・応用・注意点に踏み込んでいないか
   - 規則性・法則が対称的な構造をもつ場合(例: てこの支点からの距離は力点・作用点の双方に効く)、一方の側にしか言及がなく対応するもう一方が欠けていないか

2. **動機・意義の提示**: 本題の定義・技法に入る前に、「なぜこれを学ぶ意味があるか」が示されているか確認する。意義が前提記事や記事内の別箇所で既に十分示されている場合は繰り返しを求めない。
   - 新しい演算・記法・数(負数・分数など、既存の枠組みを拡張して定義するもの)を導入する場面で、「これを扱いたい」という目的の提示だけで終わらせず、既存の枠組みでは対応できない具体的な困りごと・実例まで踏み込んで動機を示せているか

3. **論理的飛躍**: ある主張から次の主張へ進む箇所で、読者が自力で埋められないギャップがないか吟味する。「よって」「ゆえに」「したがって」の前後で中間の推論ステップが省略されていないか特に注意する。stageが上がるほど(advanced→bachelor→master)厳密さの要求は上がる。
   - 同じ式・同じ概念が複数の場面や解釈で登場する箇所で、単に並列提示されるだけで、なぜ同じ式・概念で表せるのか橋渡しの説明がないか
   - 法則・公式を結論としてのみ提示し(天下り的提示)、既存の定義から導出する過程を省略していないか(省略が許容されるかはstageの要求水準による。観点8参照)
   - `requires`先で既出の公式・事実を、本文中で明示せず暗黙に使っている箇所がないか(例: 別記事で学んだ面積の公式を、言及せず反比例の説明に使う)

4. **不明瞭な記載**: 定義されずに使われている記号・用語、複数の意味に取れる表現(例:「ぴったり」のように文脈によって指す内容がぶれる語)、条件を示さない曖昧な形容(「多くの場合」「通常は」等)がないか探す。
   - 具体例・たとえ話の登場人物や数量設定が、本来説明したい法則と矛盾する印象を意図せず与えていないか(例: 交換法則の説明で「渡した」という言葉を使い、渡した側の手持ちが減った・0になったかのような誤解を招く設定になっていないか)
   - 太字で新規に定義した用語に、初出箇所でふりがな等の配慮があるか

5. **内部整合性**: 本文・表・リスト・図など、記事内の複数の表現形式が互いに矛盾なく対応しているか確認する。観点4(不明瞭な記載)が単一箇所の曖昧さを扱うのに対し、こちらは記事内の離れた箇所どうしの食い違いを扱う。
   - 地の文で挙げた具体例が、表やリストに漏れなく反映されているか(例: 本文で挙げた具体例が比較表に載っていない)
   - 記事内の複数箇所の記述・図が互いに矛盾していないか(例: ある節の定義と、別の節の図の表現が食い違う)

6. **読者の疑問への対応**: 記事を読み進める読者の視点に立ち、自然に浮かぶ疑問(「なぜこの定義なのか」「例外はないのか」「これは一般的に成り立つのか」等)を洗い出し、それぞれが本文中の補足、または他記事へのリンクでカバーされているか確認する。

7. **requiresとの整合性**: 本文で使われている概念のうち、`requires`に列挙されていない記事でしか説明されていないものがないか(前提漏れ)を確認する。
   - `requires`先で既に十分説明されている内容を本文で不必要に繰り返していないか
   - `requires`の連鎖をたどってもまだ登場していないはずの記法・概念(指数表記など、対象stageの読者が未習であろうもの)を、説明や注記なしに先取りして使っていないか

8. **stageにふさわしい扱い**: 対象リポジトリの`CONTRIBUTING.md`にあるstage別チェックリストと照らし合わせ、証明の有無・扱う一般性・厳密さの水準が対象stageに合っているか確認する(例: beginnerなのに形式的証明を要求している、advancedなのに直感的な説明に留まり定理が正確に述べられていない、等)。
   - 本文の主旨を理解する上で必須ではない発展的な内容(計算の工夫・補足的な性質など)が地の文に埋め込まれて難易度を押し上げていないか、Tips/Noteとして分離すべきでないか(判定基準はCONTRIBUTING.mdのTips・Note節を参照)
   - ある概念の説明位置が、読者がその時点で持っているはずの前提知識(requiresや記事内でそれまでに説明済みの内容)に対して早すぎないか

9. **具体例・計算の正確性/充実度**: 本文中の数式変形・計算例・具体例を実際に検算し、定義・定理と矛盾がないか、計算ミスや事実誤りがないか確認する。
   - 式や法則を提示した箇所に、数値を代入した具体的な計算例が伴っているか(定義・式の紹介だけで終わっていないか)
   - 物理定数など具体的な数値をもつ量を式中で使う場合、概数値と単位が示されているか(該当する場合)

10. **中立性・学説の公平な扱い**(該当する場合のみ): 複数の学説・立場が存在しうる話題を扱っている場合、特定の立場に偏った記述になっていないか確認する(MANIFEST.mdの原則を参照)。定義・計算が一意に定まる技術的な記事(数学・物理の計算手法など)では、通常この観点は該当なしとなる。

### Agent Aの出力フォーマット

観点ごとに見出しを立て、指摘がある箇所は次の形式で列挙する。

```markdown
> (該当箇所の引用)

**問題点**: ...
**改善の方向性**: ...
```

指摘がない観点は「特になし」と簡潔に述べる。良く書けている記事・これ以上手を入れる必要がない箇所に対して、体裁を整えるためだけの些末な指摘(言い回しの好み、なくても困らない一般論的な追加提案など)を捻り出さないこと。「特になし」の観点が多い記事があってよく、それ自体がその記事の完成度を示す結果である。数値スコアやパーセンテージによる評価はしない。

## Agent B: 読者ペルソナ

あなたは、この記事のstage(初級編/中級編/応用編/発展編相当)が本来対象とする読者ではあるが、その中でも読解力・集中力・記憶力が平均より低い読者です。front matterの`requires`に挙げられた前提記事の内容は一応学んだことがあるはずですが、細部までは覚えていません。難しい言い回しや、複数ステップの推論を一度で飲み込むのが苦手です。分かったふりはせず、分からなくなったら正直に「ここで分からなくなった」と反応してください。逆に、実際には引っかからなかった箇所を、指摘のノルマを埋めるために無理に「困った」と報告しないこと。

## Agent B: 読み進め方

前提知識を把握するため、対象記事のfront matterにある`requires`先の記事にざっと目を通してから、対象記事本体を読み始める。

記事を先頭から順番に、実際にその場で読んでいるように読み進める。**後方の内容を先読みして「実は後で説明されているから問題ない」といった判断をしないこと**(まだ読んでいない体で反応する)。読んでいる最中に、以下のいずれかが起きた箇所をすべて、発生順に記録する。

- 定義されていない用語・記号が使われていて意味がわからなくなった
- 前の文からどうつながるのか分からなくなった(論理が飛んだと感じた)
- 具体例が何を言おうとしているのか掴めなかった
- 図・表と本文の対応が取れずに混乱した
- 「なぜそうなるのか」「なぜこれが必要なのか」という疑問が浮かんだが、本文で答えられなかった

最後まで読み切れたか、途中で読むのをやめたくなったか(やめたくなった場合はどこでか)も記録する。

### Agent Bの出力フォーマット

発生順のログとして次の形式で列挙する。

```markdown
> (つまずいた箇所の引用)

**反応**: (ペルソナとして感じたこと・分からなくなった理由)
**該当箇所**: (見出し名など)
```

つまずきがなければ「(該当箇所の見出し)は特につまずかず読み進められた」と簡潔に述べてよい。ログの最後に、最後まで読み切れたか・途中でやめたくなった箇所があったかを一言でまとめる。

## 注意

- **両方のRvを必ずAgent toolによるサブエージェントとして実行すること**。オーケストレーター自身が10観点分析やロールプレイ読解を代行してはならない。
- **指摘のための指摘をしない**(Agent A・Bとも共通)。10観点・チェック項目すべてに何か書かなければならない、という前提で臨まないこと。実際に問題がある箇所にだけ指摘を書き、問題がない・すでに十分に書けている箇所は「特になし」で済ませる。件数の多さや網羅感を演出する目的で、些末な言い回しの好みや不要不急の追加提案、存在しないつまずきの捏造を行わないこと。
- 対象記事のstageに応じた期待水準(Agent Aが読むCONTRIBUTING.mdのstage別チェックリスト)を無視して、一律に発展編相当の厳密さを要求しないこと。
- `requires`やリンク先ファイルが実在しない(リンク切れ)場合は、Agent Aの観点6または7の指摘として含める。
- Agent Aの観点10(中立性)は、数学・物理の技術的な記事では該当しないことが多い。無理に該当箇所を探さず、該当なしなら「特になし」とする。
- 現状は1記事ずつの呼び出しを前提とする。複数記事・ディレクトリ単位の一括レビューへの拡張は将来の課題とする。

## 参考

Leadus記事に「概要レベル・定義だけで深掘りが不足している」記事が多いという課題を受け、既存記事の品質向上(OSS化に向けた土台作り)を目的に2026-07-15に作成した。

2026-08-11、math/beginner/numbers配下の四則演算5記事(自然数・足し算・引き算・掛け算・割り算)に対する人力レビュー結果を踏まえ、観点2・3・4・6・7を拡張した。未導入概念の先取り使用、新しい演算/数を定義する動機の掘り下げ不足、複数解釈の橋渡し不足、たとえ話が誤解を招く設定になっている、多義語の使用、専門用語のふりがな不足、発展的内容のTips化判断、概念の登場位置の前提知識との整合性、といった指摘が実例として得られたため、それぞれ該当する既存観点に統合した。

2026-08-15、math・phys両リポジトリの過去1ヶ月分のcommit履歴(article-critique自動適用・批評的見直し・人力レビュー各コミットの実差分)を分析し、観点を9→10に再構成した。表・リストと本文の食い違いや記事内の記述矛盾は既存観点のどれにも収まりが悪かったため、独立した観点5「内部整合性」として新設。それ以外の実例(規則性の片側のみの記述、法則の天下り的提示、requires先で既出の公式を本文中で暗黙に使う箇所、太字で新規定義した用語のふりがな漏れ、式の紹介のみで数値計算例が欠けている、物理定数を概数値・単位なしに使っている)は該当する既存観点に箇条書きとして統合した。あわせて、各観点を「定義文+着眼点の箇条書き」の形に再構成し、一文に複数チェックを詰め込んだ記述による読み落としを防いだ。

2026-08-16、Rvを「専門知を持つAgentによる学術的正確さ重視のRv(Agent A)」と「知的能力・認知能力の低いAgentによるロールプレイ追走テストRv(Agent B)」の2種類に分離し、両方を必ずAgent toolのサブエージェントとして実行する構成に再編した。従来はこのスキルを実行するAgent自身が前提情報を読み込み10観点分析を行っていたが、専門的正確さの検証と読者体験のシミュレーションは性質が異なる検証軸であるため別々のサブエージェントに委譲し、対象特定などの共通処理のみをオーケストレーターに残す設計とした。Agent Bは低い認知能力をプロンプト上のペルソナ設定だけで再現するのではなく、Agent tool起動時に`model: haiku`を指定することで実際に非力なモデルを使う設計とした。1スキル内で完結させる構成(2スキルへの分割ではなく)を採用したのは、対象記事の特定・前提情報の所在確認が両Rvに共通する処理であり、かつユーザーが両Rvをセットで(1本のレビュー結果として)利用することを想定したため。
